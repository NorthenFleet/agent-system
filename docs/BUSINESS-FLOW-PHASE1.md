# 业务流规范化第一阶段

## 1. 目标

第一阶段不替换现有 Command Center 执行器，也不引入 LangGraph 运行时。本阶段建立稳定、版本化、可验证的业务流契约，使任务规划、审批、执行、验收和记忆沉淀共享同一组语义。

设计原则：

- Command Center 是任务、审批和审计的事实主库。
- 大模型可以提议计划，但确定性规则决定计划能否进入审批。
- 领域差异放在 FlowSpec 中，状态机、风险等级、证据和幂等规则全局统一。
- 任何有副作用的操作都必须可定位、可防重和可补偿。

## 2. 契约模型

### FlowSpec

FlowSpec 由 `flow_key + version` 唯一标识，定义：

- 业务类型与阶段；
- 必须覆盖的任务能力组；
- 计划、测试、引用、审批和证据门禁；
- 最大步骤数、并行度、重规划次数和默认超时；
- 计划审批、L3 步骤审批和交付审批策略。

当前内置模板：

- `general`：通用业务；
- `software`：软件开发；
- `document`：文档生产；
- `finance`：财务处理；
- `research`：情报研究；
- `operations`：运维操作。

### StepSpec

每个步骤持久化前都会补齐：

- 阶段和单一可验证目标；
- 智能体、任务类型、依赖和工具；
- 交付物与结构化 `output_contract`；
- 验收标准和证据要求；
- `L0-L3` 风险等级和审批需求；
- 超时、最大尝试次数和幂等键；
- 影响资源、回滚方案和补偿契约。

### Artifact 与 Evidence

Artifact 是业务交付物的不可变引用，至少包含类型、URI、内容哈希和产生步骤。Evidence 是证明步骤满足验收标准的来源记录，至少包含证据类型、来源引用、摘要、采集者和时间。

第一阶段已公布完整契约，并将证据要求注入现有执行提示。Artifact/Evidence 的独立存储表与强制验收属于后续执行可靠性阶段。

## 3. 风险策略

| 等级 | 语义 | 默认尝试 | 步骤审批 |
|---|---|---:|---|
| L0 | 只读分析 | 3 | 否 |
| L1 | 可逆内部变更 | 2 | 否 |
| L2 | 重要业务变更 | 2 | 根据流程策略 |
| L3 | 不可逆或外部动作 | 1 | 是 |

付款、转账、入账、生产发布、删除数据、外部发送和权限变更至少为 L3。L2/L3 步骤缺少证据或回滚方案时，计划不得进入审批。

## 4. 计划门禁

计划持久化前依次经过：

1. 字段补齐与标准化；
2. FlowSpec 绑定与风险评估；
3. 智能体能力与工具可用性检查；
4. 依赖顺序、领域覆盖和并行资源冲突检查；
5. 验收、证据、幂等、补偿和审批策略检查；
6. 存在 blocker 时拒绝保存，否则进入 `awaiting_approval`。

领域环节缺失和资源并行冲突在第一阶段记录为 warning，方便观察现有计划质量；经过一轮实际业务数据校准后，可升级为硬门禁。

## 5. API

- `GET /api/v3/command-center/business-flows`：返回 FlowSpec、风险、状态机和数据契约。
- `GET /api/v3/command-center/capabilities`：在原智能体/工具清单中增加 `business_flow_contract`。
- Mission 详情的 `plan.raw_plan` 中增加 `flow_spec`、`risk_assessment`、`approval_policy`、`execution_policy`、`flow_validation`。

## 6. 与 LangGraph 的边界

当前 `execution_policy.runtime` 明确为 `command-center`。第二阶段如果引入 LangGraph，它必须通过 runtime adapter 消费同一份 FlowSpec 与 StepSpec；Mission、审批、交付物、证据和记忆仍由现有业务后端管理。

## 7. 第一阶段验收标准

- 所有新计划都绑定版本化 FlowSpec。
- 所有步骤都有目标、产物、验收、证据、风险、幂等和补偿契约。
- 未注册智能体、未注册工具、无效依赖、L2/L3 缺少回滚或证据时阻止计划。
- L3 动作在计划中明示标记审批，不能隐藏在普通步骤中。
- 现有状态机、人工批准和执行器保持兼容。
