# 第三阶段：证据绑定、审核修订与故障恢复

日期：2026-10-05。此报告区分真实页面操作、真实子进程终止、隔离通信故障和严格门禁离线复验，不能合并解释为正式环境全链路故障验收。

## 实现

- 证据要求和验收项增加稳定编号，编号绑定步骤、计划版本、顺序与原文。回执可引用编号，减少自然语言改写导致的误判。编号验收还要求引用本次回执中的证据来源，或绑定当前合同且具有来源与摘要的证据编号；旧版无编号回执继续走原有精确文本规则。
- 增加“反馈并重新规划”：保留失败步骤及回执，新计划重新审批。未解决补偿仍阻止恢复，不能通过此入口绕过。
- 对明确声明无副作用且 artifact_types=[] 的只读任务保留无文件合同，不再强行从 deliverables 补造文件类型。
- 规划结果中的工具、产物、验收项、证据要求及输出合同列表必须为字符串数组；对象等畸形字段在进入审批前阻断，不再静默转成字符串。
- 失败控制点显示具体原因；重新规划期间优先显示新计划状态，避免旧失败记录覆盖当前状态。
- 每次规划调用使用独立会话，仍显式传入原需求与反馈；不复用同一计划版本失败调用的会话。回归验证两次失败重试会话不同，且都不会保存回退计划。
- 已完成任务若仍有执行证据警告，顶部明确展示“任务已完成，证据仍有警告”，不把试运行完成表述为严格验收通过。

## 边界

- 子进程测试使用生产服务类和隔离 SQLite，不是正式双 worker/PostgreSQL 部署的运行中退出演练。
- 通信测试是受控本地 socket 断连，不是切断机器网络，也不能证明外部供应商的幂等能力。
- 严格复验不修改历史分数、不改变线上全局 pilot/shadow 策略。
- 只读审核的初版计划仍有“缺少内容生产”的领域模板警告；这是审校任务的模板适配问题，不能为了消除警告而执行未授权写作。

## 真实测试中的中间发现

- V1 只读审核正确返回 blocked，明确指出缺失小节，未写入文件。真实回执已经采用新 requirement_id / criterion_id。
- 通过“反馈并重新规划”进入 V2，旧失败记录保留。V2 的 evidence_required 被模型写成对象，旧规范化逻辑转为字符串后仍评分 100；在页面退回，未批准执行，并补上规划输入格式校验。
- 后一次规划未生成可解析步骤，系统暂停等待反馈，未发布回退模板或执行旧版。随后通过同一任务反馈入口重试。
- 自动检查：94 项后端回归、2 项独立进程/通信演练、11 项前端测试通过。正式前端构建通过，仍有既有大包提示和依赖弃用提示。

## 最终结论

修订复审流程已经实际跑通。救护车首次审核拒绝缺少风险小节的原稿；通天晓按新计划创建 revised.md；救护车独立复审并创建 review.md，结论 accepted。原稿 SHA-256 保持 ced3de668b7eb21897dee3baada53485533f02819f5b7a5413fee5c4ca82780a；两个新文件的校验与下载记录见 artifact-verification.json。

**严格生产验收仍未全通过。** V3 复审回执最后一项“draft.md 与 revised.md 均未被修改或删除”引用了 `exec:sha256 校验`，但该 source_ref 不存在于本次 evidence 列表，且不是有效证据编号。报告和其他证据摘要虽然写了哈希，不能替代缺失的结构化引用。严格检查器因此拒绝该回执；没有改写历史分数，也没有通过模糊匹配放行。

写作回执此前使用 evidence 编号作为引用，新增解析规则验证其编号属于当前合同且带真实来源后，离线严格复验为 100 分。此处是确定性的引用解析兼容，不是补造证据。线上历史运行发生在 pilot 下，其既有警告保留。

下一阶段应实现执行器提交前的结构化回执自检与受限修正：只允许补齐真实存在的证据引用，不重复文件副作用；随后在隔离 strict 配置中做完整任务执行与故障验收。正式部署的 PostgreSQL 双 worker 运行中故障、外部网络断开和无人干预长时间稳定性不在本次已通过范围内。
