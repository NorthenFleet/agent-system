# 第四阶段：回执自检与受限修正

日期：2026-10-05（北京时间）。本次完成回执防护实现、隔离 strict 状态流验证、历史回执复验和服务更新。正式 PostgreSQL 双 worker 的全链路故障验收仍未完成。

## 改动与行为

- 提交步骤结果时先进行严格自检，记录原始输入指纹、转换列表、严格检查结论及阻断原因；线上仍遵循既有 pilot/shadow/strict 策略。
- 受限修正只把属于当前合同、具有来源及摘要、且唯一对应来源的证据编号转换为该来源引用。原始 structured_output 保留，输入对象不修改，重复处理不会继续转换。
- 不猜测缺失引用，不改写验收结论，不补造证据，也不调用执行器重写文件。多个来源对应同一编号时不任意选择。
- 证据或协议不合格后的自动执行重试，只适用于明确无副作用且未报告已生效/未知副作用的步骤。有副作用步骤即使声称 not_applied，也暂停等待反馈。代价是部分原本可自动恢复的写操作需要人工检查。
- 原有补偿服务已经能将漏报副作用标记为 unknown；此次是附加的合同约束，并非首次实现漏报保护。
- 任务阻塞原因同时保留副作用与证据校验问题，避免执行器的成功摘要掩盖实际阻断原因。
- 执行提示增加提交前逐项检查、只修回执不重做副作用、缺少真实证据时报告 blocked 的要求。

## 仍需完成

历史 H 的缺失引用必须由新的真实核验补齐，当前自检不会把它自动变成通过。本次 strict 完整状态流使用受控测试回执，不等同于真实 OpenClaw 模型执行。进程/通信演练使用隔离 SQLite 和本地 socket，不等同于 PostgreSQL 双 worker 运行中故障或外部网络中断。

下一步应在独立 strict 环境连接真实执行器，做只读核验任务与故障恢复端到端验收，再决定是否扩大正式严格门禁。当前不能宣布无人值守生产验收全部通过。
