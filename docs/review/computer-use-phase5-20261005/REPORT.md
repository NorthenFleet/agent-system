日期：2026-10-05（北京时间）。结论：真实 OpenClaw 执行器接入独立 strict 数据库，正向任务完成、反向任务被拒绝。模型回执仍有业务状态语义不一致，服务端门禁已正确拦截。

## 范围与结果

本次通过已有 OpenClaw 网关调用 ratchet，使用新的独立会话；计划、审批、领取、步骤验收和总交付验收运行于独立 SQLite，不启动生产 worker 或通知发送循环。只读对象为第三阶段既有 revised.md；没有要求生成或修改文件。计划由测试程序构造，因此本次不验证模型规划能力。

## 反例发现

反例中模型返回 `outcome=succeeded`，摘要解释“读取与核验操作成功”，但验收结果为 fail。服务端因为明确失败的验收项阻止完成，步骤 failed，任务等待反馈。不能仅看执行器调用成功或 outcome 判定交付成功。本次保留原回执，没有把 outcome 改成 blocked 来制造一致性。

该现象说明模型业务状态表达仍需改善；确定性门禁已提供必要保护。当前样本较小，不代表模型始终能正确自检。

## 与前阶段的区别及限制

- 本次使用真实执行器返回值，不再是受控测试回执；原始输出、合同、自检记录和最终任务状态均保存。
- 字数与文件哈希已独立复核。证据来源名称由执行器声明，本报告不把它当作经过签名的工具轨迹证明。
- 隔离任务由测试程序直接调用服务，不显示在生产指挥中心。本次没有把旧任务截图当作新任务的页面验证。
- 正式 PostgreSQL 双 worker 故障接管、生产 strict 开关、完整模型规划、浏览器审批、长时间无人干预稳定性尚未在本阶段验收。
- 第三阶段历史 H 的缺失引用保持原状；本次新的只读核验不反向改写历史回执或验收结论。

## 可复现入口与证据

入口：`backend/scripts/run_phase5_strict_probe.py`。默认正向；加 `--expect-rejection` 执行反例。每次创建独立目录和数据库，调用真实执行器会产生模型使用量；不加载生产 .env、不启动通知发送器。

- 各运行目录的 contract.json、prompt.txt、executor-result.json、completed-step.json、final-mission.json、summary.json：完整验收记录。
- run-660e7388/invocation.json：反例调用的独立会话标识。正例会话元信息保存在 executor-result.json 的网关返回候选中。
- independent-file-check.json：独立字数、章节与文件哈希检查。
- verification.json：只读检查隔离数据库和返回文件校验值。

下一阶段应把实际 strict 任务接到隔离界面，验证浏览器审批、失败原因呈现及恢复动作，再推进 PostgreSQL 双 worker 故障接管；不应直接切换生产全局 strict。
